Script di pds v3: linguaggio e confini

Forgia del 2026-10-17 · Alessandro · continua la forgia pds v3 del 2026-10-13 (9 regole ferme) · obiettivo: chiudere i punti 3–4 del README dello spike

Esito

Il problema reale non era il linguaggio ma la leggibilità. La risposta è strutturale: nucleo puro in TypeScript, un solo adattatore Penpot, un solo guscio: un server MCP pds senza stato. La CI gira senza Penpot su quattro livelli; gli aggiornamenti di Penpot passano da un collaudo con un campione .penpot.

Decisioni fissate

  1. TypeScript in packages/scripts: il nucleo legge @app/contracts; niente export JSON dei contratti.
  2. Nucleo puro (dati → dati, niente disco, rete, console o codice di uscita) + adattatore readComponent, unico punto con execute_code + guscio senza decisioni.
  3. Server MCP pds come unico guscio: senza stato (rilegge live, regola 5), non scrive su Penpot, entra appena gli schemi del nucleo si stabilizzano. Nessuna CLI di prodotto.
  4. Strumenti: tokens_from_css, describe_component, verify_component, build_order, generate_component, extract_theme.
  5. I file @generated li scrive il server. generate_component non scrive con chiavi doppie o parti senza chiave.
  6. Versioni: tipi interni senza versione; file persistenti con versione del generatore + hash. Hash rotto = blocco, versione vecchia = avviso.
  7. CI su quattro livelli: nucleo · server in memoria · hash/versione · ogni classe del registro produce CSS con la Tailwind installata.
  8. Collaudo degli aggiornamenti di Penpot: campione .penpot nel repo, istanza nuova, collaudo a mano; il Penpot vero si aggiorna solo se passa.

Punti deboli sopravvissuti

  • Il server va riavviato a ogni modifica del nucleo: in sviluppo resta il dubbio "codice vecchio o nuovo?".
  • Se il server non parte, la skill resta senza strumenti: nessun piano B da CLI.
  • Il collaudo vede solo le proprietà già nel registro; una migrazione all'import del .penpot può sembrare un guasto dell'adattatore.
  • Restano aperti i punti 7, 8, 10–13 del README.
