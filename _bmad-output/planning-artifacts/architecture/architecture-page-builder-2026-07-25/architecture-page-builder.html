Page Builder — Architettura

Riscrittura greenfield full-TypeScript del page builder end-to-end: design system Penpot→codice, editor a blocchi con versioning/publish/RBAC/audit, render pubblico e integrazione commerce pluggable. Questo documento è la lettura navigabile della ARCHITECTURE-SPINE.md; il contratto vincolante resta la spine.

Paradigma: esagonale su monolite Next.js Altitudine: feature → epics 13 Architecture Decision Gate: lint 0 · 3 lenti superate 2026-07-25

01 In una riga

Monolite Next.js full-TypeScript con un core di dominio esagonale estraibile (unico punto di accesso al dominio, RBAC deny-by-default a copertura totale su lettura e scrittura), Postgres + Prisma (invariante “≤1 pubblicata” garantito dal DB via indice parziale SQL), Better Auth, oRPC, render pubblico SSG+ISR invalidato su publish, e integrazione commerce pluggable dietro il port CommerceProvider.

02 Le tre scelte che hanno definito tutto

Perché full-TypeScript e non Spring Boot

Il nodo non era Spring Boot: era JHipster che auto-generava endpoint CRUD scoperti, bypassando l’RBAC. Il tier che renderizza Puck + design system è React/TS per necessità — un backend Java sarebbe stato un tier in più, non uno al posto. Inoltre gli schemi dei blocchi e la classificazione structure/content sono già TS/Zod: un backend TS li condivide (una sola fonte di verità), un backend Java li duplica — esattamente il dolore ricorrente del legacy.

→
La competenza Java non è persa. Il giorno in cui costruirai il tuo commerce backend, potrà essere Spring Boot — ma vivrà dietro l’astrazione CommerceProvider, come adapter accanto a Shopify, non dentro il page builder. Java dove è forte (dominio commerce transazionale), TS dove è forte (rendering, design system, schemi condivisi).

Next.js e non TanStack Start

A parità di monolite fullstack, ha pesato l’ISR-on-publish: quando pubblichi una pagina, rigeneri l’HTML statico di quello slug con revalidateTag(slug). Mapping quasi perfetto col render by-slug SEO. La “cerimonia” RSC attorno all’editor Puck si riduce a due confini "use client"; la maturità dell’ecosistema abbassa il rischio per uno sviluppatore solo.

Commerce pluggable

Il page builder renderizza lui la vetrina, con i dati commerce risolti a render-time. Poiché la sorgente (Shopify e/o backend proprio) non è ancora decisa, i blocchi commerce non parlano mai a una sorgente concreta ma al port CommerceProvider. Cambiare o affiancare sorgente = cambiare un adapter, non riscrivere i blocchi.

03 Il paradigma

Esagonale (Ports & Adapters). Il core in packages/domain non conosce HTTP né React; gli adapter lo circondano.

┌─ Adapter inbound ──────────────┐ │ oRPC (editor) Route SSR/ISR │ └──────────┬──────────────┬───────┘ ▼ ▼ ╔═══════════════════════════════════╗ ║ packages/domain — CORE ║ ║ casi d'uso · RBAC · audit ║ ║ pipeline payload · PORT ║ ║ (no HTTP · no React) ║ ╚═════╤═════════╤═════════╤═════════╝ ▼ ▼ ▼ ▼ Prisma/PG BetterAuth Commerce CacheInvalidator Provider (Next ISR) │ │ Shopify Backend proprio

Dipendenze consentite (è una regola)

04 Le 13 Architecture Decision

AD-1 Core esagonale, unico accesso al dominio

Previene
Logica sparsa e CRUD scoperti (regressione legacy).
Regola
Ogni mutazione e lettura non-pubblica passa da un caso d’uso del core. Nessun accesso Prisma diretto dagli adapter inbound.

AD-2 Monolite con core estraibile

Regola
Una sola app (apps/web); il core in packages/domain senza React/HTTP, così un’API standalone futura non tocca il dominio.

AD-3 Consuma il design systemADOPTED

Previene
Due stack UI paralleli (drift react-bootstrap del legacy).
Regola
UI solo su @penpot-ds/ui + primitives. Layering tokens ← primitives ← {puck-components, ui}.

AD-4 RBAC deny-by-default; auth ≠ authzADOPTED

Regola
Better Auth dà identità + ruolo grossolano; l’authz fine (assegnazione Cliente↔pagina, content/structure) è dato di dominio nel core, su lettura e scrittura. Unica read anonima: PUBLISHED by-slug su proiezione pubblicata.

AD-5 Payload: una fonte FE/BE (Zod + classifier)

Previene
Duplicazione/drift structure-content (dolore #1 legacy) e payload non sanitizzato.
Regola
Schemi Zod + classifier vivono una volta in puck-components; il core valida, classifica e sanitizza i campi content (XSS) prima di persistere.

AD-6 Forma payload, proprietà id/versioni

Regola
Puck {content,root,zones} in jsonb; block-id client-owned immutabili; schemaVersion di puck-components; versionNumber allocato dal core in transazione, UNIQUE(page_id, version_number).

AD-7 Coerenza publish enforced dal DB

Previene
Due PUBLISHED per pagina; pagina archiviata con versione ancora pubblicata.
Regola
Indice univoco parziale Postgres (WHERE status='PUBLISHED') via migration SQL; publish/rollback/archive in una transazione che accoppia Page.status↔PageVersion.status.

AD-8 Audit nel core, sui metadati, un writer

Regola
Un unico AuditWriter scrive AuditLog canonico (actor/action/entity/timestamp/metadataDiff — non il blob). Solo ADMIN consulta.

AD-9 Render pubblico SSG+ISR via port

Regola
Core puro: espone CacheInvalidator, un adapter fa revalidateTag post-commit. Cache draft/published disgiunte; anteprima draft dinamica non cachata e protetta.

AD-10 Commerce dietro il port CommerceProvider

Previene
Lock-in su una sorgente; DTO commerce incompatibili tra blocchi.
Regola
Port canonico (metodi + DTO ProductRef/Price{amount,currency}); adapter Shopify + custom; risoluzione server-side a render-time.

AD-11 Pipeline Penpot→codice preservataADOPTED

Regola
Penpot single source dei valori; token e componenti generati e marcati @generated, mai editati a mano; rigenerazione preserva i file scritti a mano.

AD-12 Snapshot di contenuto immutabili

Regola
Ogni save crea una nuova PageVersion DRAFT; mai mutazione in-place. Il Cliente crea una DRAFT con i soli campi content editabili; structure bloccati.

AD-13 Errori tipizzati e semantica 404/403

Regola
Errori di dominio tipizzati → set oRPC fisso. Su risorsa non-pubblica non autorizzata si risponde 404 (non si rivela l’esistenza), non 403.

07 Rimandato (Deferred)

  • Sorgente commerce concreta (Shopify / backend proprio / entrambi) e suo linguaggio — il port AD-10 tiene la scelta aperta senza costo.
  • Provider DB e orchestratore container — decisione di deploy; l’envelope Docker li rende intercambiabili.
  • Logging/monitoring/backup/CI-CD di dettaglio — strategia nominata, dettaglio in implementazione.
  • Better Auth come issuer OIDC/JWT per l’ecosistema — quando esiste un secondo servizio da autenticare.
  • Policy di migrazione schemaVersion del payload — alla prima evoluzione degli schemi dei blocchi.
  • Migrazione dati dal legacy Strapi — fuori scope SPEC salvo re-ingaggio.
Nota di allineamento con lo SPEC. L’architettura ha fatto emergere contesto nuovo non presente nello SPEC originale (integrazione commerce, il page builder come storefront).
