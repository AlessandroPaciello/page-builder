Combo di punta storica: TanStack Router + Hono + tRPC + Better Auth + Drizzle + Tailwind.
- (decision) Paradigma: esagonale leggero. Core di dominio (pages/versions/publish/rollback/archive/rbac/audit/structure-content/sanitizzazione) in un package/modulo framework-agnostic (no HTTP, no React); il resto sono adapter. Binds: tutte le capability di dominio. Prevents: logica di dominio sparsa nel layer web e non riusabile/non enforced in un solo punto (regressione legacy: CRUD auto-generati scoperti).
- (decision) Topologia: monolite fullstack (non backend separato). Prevents: contratto di rete da progettare/versionare e hop extra per il render SSR, superflui per un dev solo greenfield. Il core estraibile lascia aperta una futura API standalone senza rifattorizzare il dominio.
- (decision) Meta-framework frontend/fullstack: Next.js (App Router). Binds: apps/web. Prevents: drift di rendering delle pagine pubbliche (SEO) e cerimonia sparsa. Render by-slug via SSG + ISR/on-demand revalidation invalidata su publish (revalidateTag/Path per slug); editor Puck come isola 'use client'; render pubblico come secondo confine client. Vincolo SPEC: il frontend consuma @penpot-ds/ui + primitives, non uno stack UI parallelo.
- (constraint) Nessun endpoint/azione di modifica CRUD auto-generato: ogni mutazione di pages/versions passa dai casi d'uso del core di dominio, che è l'unico punto in cui l'RBAC deny-by-default è enforced (copertura totale, vincolo SPEC).
- (direction) CONTESTO NUOVO (non nello SPEC originale): il page builder serve a definire pagine da agganciare a un microservizio commerce per creare e-commerce. Il page builder RENDERIZZA lui la vetrina (storefront). Commerce backend = Shopify e/o backend proprio, non ancora deciso. Ecosistema microservizi non ancora chiaro. → Da riflettere nello SPEC (nuova capability integrazione commerce) in fase di adozione spine come companion.
- (decision) Verdetto Spring Boot per il page builder: NO. Il tier che renderizza Puck+design system è React/TS per necessità; un backend Java sarebbe un tier aggiuntivo, non sostitutivo. La competenza Java resta valida per un eventuale commerce backend proprio, che vive DIETRO l'astrazione CommerceProvider come adapter, non dentro il page builder. Conferma full-TS Next.
- (decision) AD nuovo — Confine CommerceProvider: i blocchi commerce (es. ProductCard/ProductGrid/AddToCart) e il render non parlano mai direttamente a Shopify o a un backend commerce specifico, ma a un'interfaccia CommerceProvider astratta (adapter per Shopify, adapter per backend proprio). Binds: blocchi commerce, render storefront, integrazione dati. Prevents: lock-in su una sorgente commerce e riscrittura dei blocchi al cambio/affiancamento di sorgente. Paradigma esagonale esteso all'integrazione commerce. Sfrutta gli 'external fields' di Puck come meccanismo di aggancio dati.
- (assumption) Le pagine possono contenere sia contenuto statico (design system) sia blocchi data-driven commerce che risolvono dati a render-time via CommerceProvider. Lo storefront pubblico by-slug (CAP-11) diventa quindi anche il render della vetrina e-commerce, con SSR/ISR.
- (decision) Transport: oRPC. Binds: confine editor→dominio (apps/web). Prevents: contratto client-server non tipizzato e assenza di contratto esterno; oRPC dà type-safety end-to-end + OpenAPI gratis (valore accresciuto dall'ecosistema/consumer commerce). Abbinato a TanStack Query per autosave ottimistico.
- (decision) ORM: Prisma (scelta utente, su mio lean Drizzle non accolto — legittimo). DB: PostgreSQL. Payload Puck in colonna Json (jsonb). Binds: persistenza dominio.
- (decision) Auth: Better Auth self-hosted (adapter Prisma), tabelle identità/sessioni nel Postgres. Ruoli Admin/Editor/Cliente via plugin admin+organization+access-control. Estendibile a issuer OIDC/JWT (JWKS) come SSO dell'ecosistema microservizi (erede di Keycloak). Binds: autenticazione + ruolo grossolano.
- (decision) AD split auth/authz: Better Auth fornisce identità + ruolo grossolano; l'autorizzazione fine (es. assegnazione Cliente↔pagina) è DATO DI DOMINIO e vive nel core deny-by-default, unico punto che decide ogni operazione. Prevents: authz sparsa tra provider auth e app, e ruolo grossolano scambiato per permesso su risorsa. Onora 'RBAC copertura totale server-side'.
- (constraint) Invariante ≤1 PUBLISHED per pagina enforced a livello DB con INDICE UNIVOCO PARZIALE Postgres applicato via MIGRATION SQL ESPLICITA (non affidato al DSL Prisma: gli indici parziali in Prisma v7.4 sono preview e hanno un bug noto sui partial unique varchar, issue #29386, proprio sul pattern status='PUBLISHED'). L'app non è l'unica garante: il DB rifiuta la seconda pubblicata. Prevents: due versioni PUBLISHED per pagina per race/bug applicativo.
- (decision) Monorepo: pnpm workspaces + Turborepo esistenti. Nuovo apps/web (Next.js). Rimossi apps/strapi e apps/pagebuilder. packages/* del design system invariati (tokens/primitives/puck-components/ui/scripts/storybook). apps/web dipende su @penpot-ds/ui + primitives (no stack UI parallelo). Prevents: due stack UI paralleli (drift legacy react-bootstrap).
- (decision) Pipeline payload Puck server-side nel core: valida il payload con gli STESSI schemi Zod dei blocchi (packages/puck-components), deriva structure/content dal classifier CONDIVISO, sanitizza i campi content (XSS) prima di persist/publish. Single source of truth FE/BE. Prevents: duplicazione/drift della classificazione structure-content (field-classifier.json duplicato a mano, dolore #1 del legacy) e payload non validato/non sanitizzato.
- (decision) Rendering/caching: pagine pubbliche via SSG + ISR; su publish il core invoca revalidateTag(slug)/revalidatePath per rigenerare l'HTML statico. Anteprima draft (by-slug?version=draft) = render dinamico non cachato, protetto da auth. Prevents: HTML pubblico stantio dopo publish e leak di bozze non pubblicate.
- (decision) Flusso sessione→authz: middleware Better Auth autentica; il context oRPC trasporta principal+ruolo; ogni procedura passa il principal ai casi d'uso del core, che applicano deny-by-default. Nessuna procedura oRPC bypassa il core. Prevents: endpoint che leggono/scrivono dominio senza principal e senza check (regressione CRUD-scoperti legacy).
- (decision) CommerceProvider: interfaccia in un package dedicato; adapter Shopify (Storefront API GraphQL) + adapter custom; i blocchi commerce risolvono i dati a render-time SERVER-side via il provider (resolveData Puck). Prevents: lock-in su una sorgente commerce e chiamate commerce dirette sparse nei blocchi.
- (decision) Audit (CAP-14): audit applicativo nel core — ogni use-case di mutazione scrive audit_log (actor, azione, entità, timestamp, metadati/diff su metadati, non il blob intero). Consultabile solo da Admin. Prevents: audit parziale/aggirabile; copertura totale perché ogni mutazione passa dal core. Sostituisce Envers stack-agnosticamente, coerente col constraint 'audit su metadati, non duplicare il blob'.
- (decision) Deployment: container Docker self-host (Next standalone output), Postgres gestito/containerizzato, portabile in un ecosistema microservizi; ISR via cache handler standard Next. Dev: Docker Postgres. Prevents: lock-in di piattaforma e incoerenza col futuro ecosistema di microservizi.
