- (capability) CAP-1 Pipeline token design→codice: estrai i design token da Penpot e genera lo strato token (colori/tipografia/spacing/radii/ombre) consumato dalla UI. success: la rigenerazione produce artefatti token (CSS custom properties + scala TS) raggruppati per SET Penpot; un nuovo set produce una nuova sezione senza modifiche al codice (data-driven); i file generati sono marcati @generated e non editabili a mano.
- (capability) CAP-2 Generazione componenti design→codice: genera primitive React accessibili dai componenti Penpot (variant matrix Penpot → modello varianti). success: la pipeline emette componente+test+story+barrel; i file scritti a mano sono preservati (skip salvo --force); un gate di completezza artefatti passa in CI.
- (capability) CAP-3 Libreria di primitive accessibili: libreria di componenti UI headless/accessibili organizzati per dominio (data-display, inputs, feedback, layout, navigation, overlays). success: ogni componente interattivo rispetta la a11y baseline (focus visibile WCAG AA, stato=testo+colore, ARIA corretto), verificato da test axe.
- (capability) CAP-4 Blocchi Puck: primitive del design system incapsulate come blocchi del page-builder con campi validati da schema e controlli guidati dai token, aggregati in un'unica config, con slot annidabili. success: l'editor renderizza i blocchi; una modifica ai token spacing/radii si propaga sia agli stili sia alle opzioni dei campi dei blocchi.
- (capability) CAP-5 Composizioni di prodotto (ui): componenti composti con semantica dell'editor page-builder (LifecycleBadge, SaveStateIndicator, TopBar, PageList, VersionList, EmptyState), costruiti solo su primitive+token. success: le composizioni sono usate dalla shell dell'editor; regola di confine rispettata: una primitiva non conosce il dominio page-builder.
- (capability) CAP-6 Authoring drag-and-drop delle pagine: un utente autenticato costruisce/modifica una pagina visivamente con l'editor a blocchi; il layout è persistito come payload strutturato a blocchi (forma Puck {content, root, zones}, con schemaVersion e id di blocco stabili). success: una pagina reale fa round-trip lossless (salva→ricarica identico) e viene renderizzata.
- (capability) CAP-7 Autosave/salvataggio bozza: salva il layout corrente come nuova versione DRAFT. success: il salvataggio crea una nuova versione DRAFT; lo stato salvato/non-salvato è comunicato all'utente (aria-live).
- (capability) CAP-8 Versioning + publish: cronologia versioni per pagina; il publish promuove una versione a PUBLISHED; al più una versione PUBLISHED per pagina (eventuale precedente retrocessa a DRAFT atomicamente). success: pubblicare una seconda versione retrocede la prima; l'invariante '≤1 PUBLISHED per pagina' regge.
- (capability) CAP-9 Rollback: ripristina una pagina a una versione precedente (la promuove a PUBLISHED, retrocede l'attuale PUBLISHED a DRAFT). success: dopo il rollback la versione scelta è quella pubblicata.
- (capability) CAP-10 Lifecycle pagina (archive/restore): stati DRAFT/PUBLISHED/ARCHIVED; l'archiviazione preserva le versioni; il restore riporta a DRAFT. success: le versioni di una pagina archiviata sono preservate; il restore riporta a DRAFT.
- (capability) CAP-11 Render pubblico per slug: rende una pagina tramite slug — versione pubblicata di default, ultima bozza su richiesta. success: la lettura by-slug restituisce il payload pubblicato di default e la variante draft su richiesta.
- (capability) CAP-12 Authoring basato sui ruoli (RBAC): ruoli Admin/Editor/Cliente governano le operazioni, deny-by-default, enforcement server-side. Admin=tutto incl. audit; Editor=crea/salva/pubblica/rollback/archivia ma NO audit; Cliente=modifiche solo-contenuto su pagine esplicitamente assegnate, niente publish/rollback/archive/create. success: il server rifiuta le operazioni fuori-ruolo a prescindere dalla UI; un Cliente salva solo-contenuto su pagina assegnata ma non può pubblicare. Dettaglio → rbac-matrix.md.
- (capability) CAP-13 Classificazione campi structure vs content: una single source of truth classifica i campi di ogni blocco come structure o content; pilota sia i permessi dell'editor (chi modifica cosa) sia la sanitizzazione lato server. success: i campi content sono sanitizzati al salvataggio/publish; campi/componenti sconosciuti trattati come content di default (fail-safe).
- (capability) CAP-14 Audit trail: storico immutabile di chi ha cambiato cosa e quando su pagine/versioni, consultabile dall'Admin. success: un admin recupera la cronologia revisioni per una pagina e per utente.

- (decision) CAP-11 (render pubblico by-slug) esteso: la pagina pubblicata è anche il render della vetrina e-commerce (SSR/ISR), non solo contenuto statico. I blocchi commerce risolvono i dati a render-time via il provider (CAP-15).
